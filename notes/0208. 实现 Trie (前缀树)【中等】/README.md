## 1. 题目描述

- [leetcode](https://leetcode.cn/problems/implement-trie-prefix-tree/)

[Trie][1]（发音类似 "try"）或者说前缀树是一种树形数据结构，用于高效地存储和检索字符串数据集中的键。这一数据结构有相当多的应用情景，例如自动补全和拼写检查。

请你实现 Trie 类：

- `Trie()` 初始化前缀树对象。
- `void insert(String word)` 向前缀树中插入字符串 `word`。
- `boolean search(String word)` 如果字符串 `word` 在前缀树中，返回 `true`（即，在检索之前已经插入）；否则，返回 `false`。
- `boolean startsWith(String prefix)` 如果之前已经插入的字符串 `word` 的前缀之一为 `prefix`，返回 `true`；否则，返回 `false`。

---

示例：

```txt
输入
["Trie", "insert", "search", "search", "startsWith", "insert", "search"]
[[], ["apple"], ["apple"], ["app"], ["app"], ["app"], ["app"]]
输出
[null, null, true, false, true, null, true]

解释
Trie trie = new Trie();
trie.insert("apple");
trie.search("apple");   // 返回 True
trie.search("app");     // 返回 False
trie.startsWith("app"); // 返回 True
trie.insert("app");
trie.search("app");     // 返回 True
```

---

提示：

- `1 <= word.length, prefix.length <= 2000`
- `word` 和 `prefix` 仅由小写英文字母组成
- `insert`、`search` 和 `startsWith` 调用次数总计不超过 `3 * 10^4` 次

- 时间复杂度：`insert`/`search`/`startsWith` 均为 $O(m)$，其中 $m$ 是单词或前缀的长度
- 空间复杂度：$O(T)$，其中 $T$ 是所有插入单词的字符总数

算法思路：

- 每个节点包含子节点映射和是否为单词结尾的标记
- `insert`：逐字符遍历，不存在则创建新节点，最后标记结尾
- `search` 和 `startsWith` 复用前缀搜索逻辑，区别在于是否检查 `isEnd`

## 3. 【AI】结合示例具体走一遍流程

用题目示例完整走一遍。

```txt
Trie trie = new Trie();
trie.insert("apple");
trie.search("apple");    // true
trie.search("app");      // false
trie.startsWith("app");  // true
trie.insert("app");
trie.search("app");      // true
```

### 3.1. 初始

```text
root { children: {}, isEnd: false }
```

### 3.2. `insert("apple")`

从 root 出发，逐字符建节点，最后打上 `isEnd`。

| 步  | 字符 | 动作                           |
| --- | ---- | ------------------------------ |
| 1   | `a`  | root 下没有 `a` → 新建；走到 a |
| 2   | `p`  | a 下没有 `p` → 新建；走到 p    |
| 3   | `p`  | 再建一层 p                     |
| 4   | `l`  | 新建 l                         |
| 5   | `e`  | 新建 e，设 `e.isEnd = true`    |

```text
root
 └─ a
     └─ p
         └─ p
             └─ l
                 └─ e ●   ← apple 结束
```

### 3.3. `search("apple")`

走 `_searchPrefix("apple")`：`a→p→p→l→e` 全程通，落到 `e`。

`e.isEnd === true` → **true**。

### 3.4. `search("app")`

走 `_searchPrefix("app")`：`a→p→p` 通，落到第二个 `p`。

但这个 `p` 的 `isEnd` 仍是 `false`（只插过 apple，没插过 app）→ **false**。

```text
... → p → p ← 停在这里，不是单词结尾
         └─ l → e ●
```

### 3.5. `startsWith("app")`

同样走 `_searchPrefix("app")`，节点存在即可，**不看** `isEnd` → **true**。

### 3.6. `insert("app")`

再走一遍 `a→p→p`，路径已存在，不用新建；到第二个 `p` 时设 `isEnd = true`。

```text
root
 └─ a
     └─ p
         └─ p ●       ← app 结束（刚标记）
             └─ l
                 └─ e ●  ← apple 结束
```

### 3.7. `search("app")`

又走到第二个 `p`，这次 `isEnd === true` → **true**。

### 3.8. 对照代码

| 操作         | 关键逻辑                                 |
| ------------ | ---------------------------------------- |
| `insert`     | 缺边就 `new Trie()`，走完 `isEnd = true` |
| `search`     | 前缀存在 **且** `node.isEnd`             |
| `startsWith` | 前缀存在即可（`node !== null`）          |

公共前缀 `app` 只存一条链；`apple` 在后面多挂 `l→e`，这就是 Trie 省空间、查前缀快的原因。

## 4. 【AI】解释一下什么是前缀树 Trie？

**前缀树（Trie）**，也叫字典树或单词查找树，是一种专门用于**快速检索字符串**的多叉树数据结构。

它的核心设计思想是 **“用空间换时间”**，通过将字符串的公共前缀合并存储，来极大提升查找效率。

为了让你直观理解，我们先看一个例子：假设树中插入了 `["cat", "car", "dog", "deer"]`，它的结构长这样：

```text
        (根节点)
       /        \
      c          d
     / \        / \
    a   a?     o   e
   / \   \    /   / \
  t   r   ?  g   e   r
              (结束) (结束)
```

---

### 4.1. 核心结构（怎么组成的？）

Trie 的节点通常包含两个部分（以标准字母 Trie 为例）：

- **子节点指针（Children）**：通常是一个大小为 26（对应 26 个小写字母）的数组或哈希表，指向下一级字符。
- **标志位（isEnd）**：一个布尔值，标记**从根节点到当前节点的路径**是否构成一个完整的单词。

**关键规则**：根节点**不保存**任何字符，每个子节点保存一个字符。从根节点到某个标记为 `isEnd=True` 的节点的路径，就组成了一个完整的单词。

---

### 4.2. 核心操作（怎么工作的？）

**① 插入（Insert）**
例如插入单词 `"cat"`：

- 从根节点开始，看有没有 `'c'`，没有就新建。
- 移动到 `'c'` 节点，看有没有 `'a'`，没有就新建。
- 移动到 `'a'` 节点，看有没有 `'t'`，没有就新建。
- 移动到 `'t'` 节点，将该节点的 `isEnd` 标记为 `True`。

**② 查找（Search）**
例如查找 `"car"`：

- 顺着根 → `'c'` → `'a'` → `'r'` 查找，如果路径完整且 `'r'` 节点的 `isEnd` 为 `True`，则存在。
- 如果查 `"ca"`，虽然路径存在，但 `'a'` 节点标记为 `False`（除非 `"ca"` 也是个单词），则返回 `False`。

**③ 前缀查询（StartsWith）**
这是 Trie 最强大的功能。查询前缀 `"ca"`：

- 只需要检查是否存在根 → `'c'` → `'a'` 这条路径。只要路径存在，无需管结尾标记，直接返回 `True`。

**时间复杂度**：以上所有操作的时间复杂度都是 **O(L)**，其中 L 是单词的长度。**这完全不受数据量大小的影响**（比如 1 万个单词和 1 亿个单词，查找一个词的时间是一样的）。

---

### 4.3. 优缺点（好在哪里？差在哪里？）

- **优点**：
  - **极致的前缀检索**：非常擅长处理 `"查找所有以...开头的词"`（如搜索引擎的自动补全）。
  - **节省存储（针对长前缀）**：如果大量单词拥有相同前缀（如 `"test"`, `"tester"`, `"testify"`），它们只共享一份 `"test"` 空间。
- **缺点**：
  - **极度消耗内存**：如果每个节点都开一个长度为 26 的数组，而只存一个字母，空闲指针会浪费大量空间（空间换时间）。
  - **对中文不友好**：中文没有有限的字母表，通常需要用哈希表代替数组来做子节点，或者转为拼音/Unicode 处理。

---

### 4.4. 实际应用场景（在哪里见过？）

- **搜索引擎的搜索框**：你输入 `"app"`，瞬间下拉出 `"apple"`, `"application"`, `"appetite"` —— 这就是 Trie 在做前缀匹配。
- **通讯录搜索**：输入电话号码前缀，快速检索匹配的联系人。
- **IP 路由表（最长前缀匹配）**：路由器查找目的 IP 时，会使用一种变种的二进制 Trie（Patricia Trie）找到匹配最长的路由条目。
- **输入法词频统计**：可以用来储存词库，并配合计数器实现高频词汇优先显示。

---

### 4.5. 与哈希表（HashMap）的对比（面试重点）

既然哈希表查 `"cat"` 也是 O(1)，为什么还要用 Trie？

| 对比维度     | **哈希表 (HashMap)**                           | **前缀树 (Trie)**                                 |
| :----------- | :--------------------------------------------- | :------------------------------------------------ |
| **前缀查询** | 无法实现（必须遍历所有 Key）                   | **原生支持**，极快                                |
| **查找时间** | O(1)（理论），但哈希碰撞或长字符串哈希计算耗时 | 严格 O(L)（L=单词长度）                           |
| **有序性**   | 无序（遍历是乱序的）                           | 按字典序排列（深度优先遍历即可排序）              |
| **空间**     | 存储 N 个词需要 N 个完整字符串空间             | 有共享前缀时极省，无共享前缀（如 a,b,c...）时极费 |

---

### 4.6. 💡 进阶小贴士（变种）

在实际工程中，为了避免内存爆炸，通常会使用 **压缩前缀树（Radix Tree / Patricia Trie）**，它将只有一个子节点的连续路径压缩成一条边（例如 `"ca"` 直接作为一个节点挂在 `'c'` 下），极大减少了树的高度和节点数量，这也是 **Redis** 底层存储数据结构的核心之一。
